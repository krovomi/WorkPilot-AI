# skills/ — the source of truth for agent skills

Everything an agent can be taught lives here. `.agents/skills/`, `.gemini/commands/`,
`.claude-plugin/` and the other harness directories are **generated** from it — never
edited by hand. CI (`pnpm run skills:check`) fails if they drift.

```bash
pnpm run skills:list       # what this project resolves to, and why the rest does not
pnpm run skills:build      # regenerate every enabled harness output
pnpm run skills:check      # fail on drift (the CI gate)
pnpm run skills:bootstrap  # install runtimes that gated skills are waiting on
python3 scripts/skills_cli.py why <skill>
```

## Layout

```
skills/
  <pack>/
    pack.json            name, semver, default toolchain targets, optional bootstrap
    <skill>/SKILL.md     the skill, plus any scripts/ examples/ reference.md beside it
    agents/<name>.md     subagent personas belonging to the pack
```

| Pack | What it is |
|---|---|
| `dotnet` | .NET: modern stack (C# 14 / ASP.NET Core 10) plus a .NET Framework 4.8 specialist |
| `tooling` | toolchain-agnostic: building MCP servers, driving web apps under test |
| `comms` | business communication and brand guidelines |
| `bmad` | BMAD Method v6, vendored and pinned — needs `skills:bootstrap` |

## Authoring a skill

Frontmatter carries what a human decides. Everything the build can derive (pack name,
pack version, content hash) is injected at build time and must **not** be written here —
that is what keeps the two from drifting.

```yaml
---
name: my-skill
description: What it does and when to use it. The first sentence matters most —
  harnesses truncate this in their skill listing.
paths: "**/*.cs,**/*.csproj"        # optional: auto-activation globs
metadata:
  workpilot:
    targets: { dotnet: ">=10.0" }   # optional: overrides the pack default
    requires: { runtime: "_bmad/core/tasks/workflow.xml" }   # optional
    min_effort: medium              # optional
---

Instructions here.
```

`targets: {}` written explicitly means "applies everywhere" and overrides a restrictive
pack default. Omitting the key inherits the pack's.

## The two axes

A skill is kept only when both hold:

* the **pack** satisfies any pin in the project's `.workpilot/skills.toml`;
* the **toolchain targets** match what the project is on (declared there, or detected
  from `package.json`, `.nvmrc`, `pyproject.toml`, `go.mod`, `Cargo.toml`, `*.csproj`).

That is what lets a project on .NET Framework 4.8 keep resolving to the guidance written
for it while newer variants ship alongside. New versions arrive as additions; an existing
variant is never rewritten in place.

## Runtime gates

`requires` keeps a skill out of the build until it can actually run:

* `runtime: <path>` — a file that must exist, relative to the project root
* `command: <name>` or `command: [a, b]` — an executable on `PATH`, any one of them

The BMAD pack is the reason this exists. Its 76 wrappers are pointers into `_bmad/`,
a tree generated by BMAD's own installer and too large to commit. Before the gate, all
76 appeared in the Kanban command palette on a fresh clone and every one of them failed
on invocation.

## Harnesses

`capabilities/harnesses.yaml` says where each tool looks. `.agents/skills/` is the
canonical output: the WorkPilot backend serves it to the Kanban palette regardless of
which LLM drives the task, and Copilot, Codex, Cursor, Amp and Gemini read it natively.
The rest are mirrors for tools that only look in their own directory.
