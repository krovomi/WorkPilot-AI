00 · Lecture sans prérequis technique

WorkPilot AI expliqué en dix minutes

Cette page s'adresse à un comité d'architecture et à toute personne qui veut comprendre ce que fait le produit sans lire de code. Les vues suivantes (01 à 09) donnent les preuves, fichier par fichier.

Ce que fait WorkPilot, en une image

Imaginez un atelier. Vous déposez une demande sur un tableau (le Kanban) : « ajouter un export PDF », « corriger ce bug ». Un chef d'atelier (l'agent planner) lit la demande, visite le chantier (votre code) et écrit un plan en étapes. Un compagnon (l'agent coder) réalise chaque étape, dans une copie isolée du chantier (un worktree) pour ne rien casser. Un contrôleur (l'agent QA) vérifie le résultat contre la demande, renvoie ce qui ne va pas, et une personne relit avant d'intégrer.

Les « agents » sont des modèles d'IA auxquels WorkPilot donne un rôle, des règles et des outils limités. Le modèle lui-même peut venir de plusieurs fournisseurs (providers) : Anthropic (Claude), OpenAI, GitHub Copilot, Google, Mistral, ou un modèle local sur la machine. WorkPilot est l'atelier ; le provider est l'artisan qu'on y fait venir.

Le trajet d'une carte, en sept étapes

C'est le trajet d'une fonctionnalité. Depuis le 16 octobre, le type de la carte (bug, correctif urgent, enquête, exploitation « RUN », refactoring, tests, documentation, étude) est reconnu sans dépenser de jeton, affiché sur la carte, et choisit un trajet plus court quand le trajet complet n'a pas de sens : un bug est d'abord reproduit ; une enquête rend un rapport et n'écrit pas de code ; une tâche RUN produit une procédure qu'une personne relit avant toute exécution.

  1. Spécification — la demande est reformulée en exigences vérifiables ; la complexité est estimée.
  2. Planification — un plan en sous-tâches ; une personne l'approuve (arrêt volontaire).
  3. Préparations sans IA — documentation des bibliothèques, pièces jointes lues, design system si l'interface est touchée. Aucun jeton dépensé.
  4. Codage — une session par sous-tâche, méthode « test d'abord ». L'agent peut confier une question à un sous-agent spécialisé (lancer les tests, cartographier un module) qui travaille à part et ne rend que sa conclusion.
  5. Revue — une lecture critique du code produit, avec des angles choisis selon l'effort demandé (correction, sécurité, conformité…).
  6. Vérification et QA — l'application est lancée pour de vrai ; les critères d'acceptation sont contrôlés ; les défauts reviennent au compagnon.
  7. Intégration — relecture humaine, puis fusion dans la branche principale. Ce qui a été appris (pièges, conventions) est rangé dans une mémoire partagée pour la prochaine carte.

Trois garde-fous qu'il faut connaître

  • Un agent n'a que les outils de son rôle. Un relecteur ne peut pas modifier le code ni lancer une commande ; c'est écrit dans une table et vérifié par un test, sur tous les providers.
  • Tout ce qui vient de l'extérieur est une donnée, jamais un ordre. Le texte d'un ticket, d'une page web ou d'une pièce jointe est nettoyé et encadré avant d'entrer dans un prompt ; une instruction qui s'y cache n'est pas exécutée.
  • Aucun secret ne sort de son coffre. Clés et jetons sont chiffrés au repos, masqués dans les journaux, et un contrôle bloque un commit qui en contiendrait un.

Référence : docs/rules/security.md (règles S1 à S8).

Ce que coûte une carte, et comment on le contient

Chaque échange avec un modèle se paie en jetons (grossièrement, des morceaux de mots). WorkPilot contient la dépense de quatre façons : il ne joue que les phases que le niveau d'effort choisi achète (le profil affiché avant le build est ce qui s'exécute) ; les préparations qui n'ont pas besoin d'IA sont faites par du code ordinaire ; un sous-agent ne rend au parent qu'une conclusion bornée, jamais son travail complet ; et les résultats d'outils trop longs sont paginés ou déposés dans un fichier au lieu d'être relus à chaque tour.

Petit glossaire

ProviderLe fournisseur du modèle d'IA (Anthropic, OpenAI, GitHub Copilot, Google, Mistral, un modèle local…). WorkPilot sait les piloter tous ; capabilities/providers.yaml dit honnêtement ce que chacun sait faire.
Agent / agent_typeUn rôle donné à un modèle : planner, coder, QA reviewer… Chaque rôle a sa liste d'outils autorisés.
Sous-agent, rosterUn spécialiste (lanceur de tests, auditeur de sécurité, cartographe du code…) qu'un agent peut appeler. Le roster est l'équipe de spécialistes mise à disposition d'une phase. Un sous-agent travaille dans son propre contexte et ne rend qu'une conclusion bornée.
Délégation émuléeQuand le fournisseur n'a pas de mécanisme natif de sous-agents, WorkPilot le reproduit : un outil delegate dans la session, et une session enfant du même fournisseur par délégation.
Workflow, phaseLe parcours d'une carte, décrit dans un fichier YAML lisible, un par type de carte (workflows/<type>/workflow.yaml ; feature-build pour une fonctionnalité). Une phase est une étape ; certaines ne coûtent aucun jeton (déterministes) ; une phase peut nommer un remplaçant (fallback:) joué quand son implémentation n'est pas installée dans le projet.
Phase irréversibleUne phase qui change quelque chose qu'abandonner la branche ne défait pas (déploiement, purge, migration de données). Le build s'arrête avant elle, montre ce qui serait joué, et n'exécute rien tant qu'une personne n'a pas repris la tâche.
Type de carteCe que la carte demande : fonctionnalité, bug, correctif urgent, enquête, exploitation (RUN), refactoring, tests, documentation, étude. Reconnu sans modèle, affiché sur la carte, modifiable ; il choisit le workflow.
EffortLe niveau de réflexion demandé (none → ultrathink). Il décide des phases jouées et de la profondeur de la revue.
SkillUn mode d'emploi en Markdown qu'un agent lit pour faire une chose bien (lancer une vérification, écrire un plan de test). La source est skills/ ; les copies lues par les outils sont générées.
BMADUne méthode agile outillée (50 skills vendorisés en v6.12). Appelée dans un workflow seulement là où elle apporte un document (brainstorm, PRD, recherche), et seulement si le projet cible l'a installée ; sinon l'équivalent WorkPilot joue à sa place, et le profil le dit.
WorktreeUne copie de travail isolée du dépôt, une par carte : l'agent y travaille sans toucher la branche principale.
Cerveau partagéLa mémoire des builds (un coffre Obsidian versionné) que tous les agents lisent et écrivent : pièges, conventions, décisions.
Jeton (token)L'unité facturée par un fournisseur d'IA ; un mot vaut environ un jeton et demi. Tout ce qui est dans le contexte d'une session est payé à chaque tour.
01 · Vue macroscopique

Ce que WorkPilot AI exécute réellement

Une application Electron pilote un backend Python ; toute interaction LLM passe par une seule fabrique (core/client.py) qui choisit le provider, les outils, les serveurs MCP et le roster de sous-agents. Depuis le premier audit, le cahier de nettoyage a été exécuté lot après lot (L1 à L17) : chaque type d'agent n'a plus que les outils qu'il déclare, le pipeline payé est le pipeline exécuté, le code mort a été retiré et docs/CLAUDE.md ne porte plus que les règles. Ce qui est déjà sain (et l'est resté)

  • Une seule fabrique de clients ; la matrice capabilities/providers.yaml décide sous-agents (natif / émulé / aucun), effort et famille de surcharges de skill. Le roster est attaché en un seul point (create_agent_client) pour tous les providers.
  • Une règle ne vit plus qu'à un endroit : sous-agents dans agents/subagents/, détection de pile dans project/stack.py, globs de surface en alias YAML, tests sous tests/ avec une seule configuration pytest.
  • Les nouvelles features réutilisent l'existant : verify s'appuie sur AppEmulatorRunner, mobile.stacks, docintel ; uiux sur le cerveau et la prévision du plan.
  • Les phases conditionnelles sont maintenant décidées sur les fichiers prévus par le plan (narrow_to_forecast) : une tâche backend ne paie plus les phases web.
  • Le profil affiché signale les implémentations manquantes (CLI et carte WorkflowProfileCard).
  • rtk, watermarks, read_guard, cerveau, uiux et verify sont branchés une fois : fabrique pour le SDK Claude, tool_executor pour les autres providers.

09 · Feuille de route · types de tâche Kanban

Traiter chaque type de carte à sa façon

Résumé lisible de docs/architecture/kanban-task-types.md (PR #455, mergée le 15 oct.). Lots 0 à 3 livrés (PR #460, #461, #462 et la PR du lot 3) : cette vue dit ce que chacun ajoute, ce qu'il réutilise, ce qu'il coûte et ce qu'il prouve. Le lot 3 s'appuie sur la délégation de la PR #454 pour donner un lanceur de tests à tout provider.

Le constat, en une phrase

WorkPilot savait construire une fonctionnalité et jouait ce parcours pour toute carte, quelle que soit son intention : un bug payait des phases de feature, un incident attendait la QA, une tâche d'exploitation n'avait pas de place (). Depuis les lots 0 à 3 (PR #460, #461, #462 et la PR du lot 3) : le type est une donnée de la carte, chaque type a son workflow, BMAD n'entre que là où il apporte un document, et une tâche RUN est jouée par WorkPilot derrière une pause avant l'irréversible. Restent les lots 4 à 6 : les rosters et prompts par type, l'origine de la carte qui renseigne le type, la mesure.

Cinq principes

  1. Un type = un workflow YAML, jamais un if dans le coder : la spécialisation est de la donnée, relue par les tests sur un clone frais.
  2. Classer avant de payer : catégorie ou label (0 jeton) → mots du titre (0 jeton) → un seul appel à faible effort en cas de doute. Le type est affiché et modifiable avant le build.
  3. BMAD est une capacité, pas une phase par défaut : appelé par impl: là où il apporte un document, remplacé par l'équivalent WorkPilot (fallback:) quand le projet ne l'a pas — jamais sauté en silence.
  4. Tout provider : aucune phase ne nomme un outil propre à Claude ; les contrôles déterministes tournent sans modèle.
  5. Chaque jeton a un lecteur : un rapport que personne ne lit n'est pas produit ; un type court a un workflow court.

Ce que le plan refuse

  • Un if kind == "bug" dans coder.py ou build_commands.py.
  • Une phase BMAD obligatoire, ou présente dans un profil sans _bmad/.
  • Un type décidé par un appel modèle quand une catégorie ou un label le donnait déjà.
  • Une étape RUN jouée par le modèle : il écrit la procédure, Python l'exécute.
  • Un outil, un roster ou une phase qui n'existe que sur Claude.

Pour un comité : les questions à trancher

  1. Le mock _bmad/ — tranché (PR #458) : il échoue (code 2), la palette le masque, le moteur et le runner ne le comptent jamais comme le vrai runtime ().
  2. RUN — tranché (lot 3) : worktree seulement tant que .workpilot/environments.toml n'est pas déclaré ; un environnement nommé mais non déclaré bloque au lieu de rediriger ; le fichier nomme des variables, jamais des valeurs. La pause a lieu avant la phase entière, pas avant chaque étape irréversible : la personne relit la liste complète et reprend une fois.
  3. Hotfix : la relecture humaine passe du planning au merge. Est-ce acceptable pour l'équipe qui opère la prod ?
  4. Mesure : le lot 6 peut précéder les autres pour avoir une base de comparaison (jetons par type aujourd'hui).
