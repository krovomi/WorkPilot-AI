# F149 · Des réglages de tokens annoncés n'atteignaient pas le modèle

- **Sévérité** moyenne · **trouvé par** l'analyse des tokens des tâches Kanban demandée par Leub
  (2026-11-03), croisée avec la documentation de chaque provider.
- **Preuve** (avant) :
  - `_add_effort` sortait si le modèle ne contenait pas « opus », alors que `effort_plan`
    annonçait `native` pour tout modèle Claude : une carte Sonnet 5.5 en « low » tournait en
    `high`.
  - `CompatibleProviderAgentClient` n'envoyait aucune clé de cache. Mistral documente un cache
    activé par `prompt_cache_key` (tokens relus à 10 % du prix), xAI un header `x-grok-conv-id`
    qui envoie une conversation vers le serveur qui détient son cache.
  - `ENABLE_PROMPT_CACHING_1H=1` était posé pour toute session Claude : une écriture d'une heure
    coûte 2× l'entrée contre 1,25× pour cinq minutes, alors que les tours d'une session se
    suivent à quelques secondes et que deux cartes ne partagent pas de préfixe.
- **Correction** : `claude_takes_effort` (table par famille et version), `compatible_cache_routing`
  (clé hachée par tâche et phase, dans le corps pour Mistral, dans un header pour Grok, rien pour
  DeepSeek dont le cache est automatique), et plus de TTL forcé : Claude Code donne une heure sur
  un abonnement dans son forfait et cinq minutes dès que l'usage est facturé.
- **Tests** : `tests/core/test_claude_add_effort.py`, `tests/core/test_effort_plan.py`
  (`TestClaudeEffortModels`), `tests/core/test_llm_optimization.py`
  (`TestCompatibleCacheRouting`), `tests/core/test_openai_loop.py`,
  `tests/core/test_create_client_characterization.py`.
