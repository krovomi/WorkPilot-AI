# F132 · En mode serveur, le flux en direct et l'environnement des runs ne s'arrêtaient pas au tenant

- **Sévérité** haute · **trouvé par le plan multi-tenant du 31 octobre (MT0)** · **corrigé par le
  lot MT0**
- **Constat** : le serveur WebSocket acceptait tout jeton valide sur tout canal, y compris après
  un changement de canal (`init_session`), et l'événement publié choisissait lui-même son canal.
  Le run manager démarrait chaque run avec `dict(os.environ)`, contre la règle S4
  (environnement construit, pas hérité). Mode local inchangé.
- **Correction** :
  - `server/authz/ws_channels.py` : deux familles de canaux, `project:<id>` et `run:<id>` ; un
    utilisateur actif lit le canal d'un projet où il a un rôle dans l'organisation où il agit
    (même règle que les routes, `get_project_role`), écrit dans le chat et pilote la session à
    partir du rôle `member` ; seul un jeton de service publie ; le jeton d'un run n'ouvre que
    `run:<son id>`. Tout autre nom de canal est refusé.
  - `streaming/websocket_server.py` : la décision s'applique à la connexion (fermeture `4403`), au
    changement de canal et à chaque message ; en mode serveur un événement part sur le canal de
    la connexion. Des réglages serveur illisibles laissent le serveur fermé au lieu de le
    rabattre en mode local.
  - `server/services/run_env.py` : l'environnement d'un run est celui du serveur moins chaque
    variable que le serveur lit pour lui-même (`SERVER_ONLY_ENV`), plus les valeurs du run ;
    `tests/backend/test_run_env.py` échoue quand une nouvelle variable `WORKPILOT_*` du paquet
    `server` n'est pas classée.
  - Le jeton de streaming d'un run porte son identifiant (`run`).
- **Garde-fous** : `tests/backend/test_ws_channel_authz.py`, `tests/backend/test_run_env.py`.
