# F143 · Chaque PR attendait 25 minutes de pytest Windows et un double passage Linux en 3.13

- **Sévérité** moyenne · **trouvé par** Leub (2026-11-02, « on ne passe pas 15 minutes par PR »)
  · **corrigé par** la PR « ci : shards pytest et 3.12 seule sur les PR »
- **Preuve** (avant) : durées par job des runs CI 41442737391, 41441464938, 41429273903,
  41427760274, 41424344525 : Windows 23,2 à 26,3 min, Linux 3.13 17,6 à 18,6 min (dont
  10 min de couverture), Linux 3.12 6,6 à 8 min, macOS 7,6 à 10,9 min.
- **Correction** : matrice 3.12 sur trois OS, en shards par fichier de test équilibrés par la
  durée de chaque fichier sur Windows (`tests/ci_durations.json`, relevée sur un run complet ;
  équilibrer au nombre de tests donnait des shards de 150 à 490 s) ; couverture combinée dans `coverage-python` (requis par `CI Complete`) ; 3.13 dans
  `test-python-latest`, sur push seulement. Les shards ont révélé des tests qui ne passaient que dans l'ordre complet : un test qui
  réimporte un module sous `patch.dict(sys.modules)` laissait l'attribut du paquet
  (`core.client`, `core.simple_client`) sur une copie que `from core.client import x` ne lit
  pas, et le `monkeypatch` d'un test suivant ne servait à rien. `tests/conftest.py` réaligne ces
  attributs sur `sys.modules` avant chaque test. La variable de shard est retirée de
  l'environnement pour que les tests qui relancent pytest en sous-processus collectent leurs
  propres fichiers.
- **Garde-fou** : `tests/test_ci_shard.py` (les shards couvrent chaque test une fois et restent
  équilibrés).
