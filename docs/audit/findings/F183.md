# F183 · Un agent du Contrôle de Mission restait « running » à 0 token sans jamais appeler son modèle

- **Sévérité** haute · signalé par Leub le 2026-11-14 : un « Agent Coder » (anthropic, Claude
  Sonnet 4.5) lancé sur « say HELLO » restait « running » à 0 %, 0 token, 0 $, le temps
  avançait, le journal ne montrait que « Agent Created » puis « Agent Started ».
- **Cause** : `MissionControlOrchestrator.start_agent` ne faisait que `slot.start(task)`.
  La route `/agents/{id}/update`, prévue pour qu'un processus d'agent rende compte, n'avait aucun
  appelant : rien ne lançait le modèle. Pause et reprise ne changeaient qu'un statut.
- **Correction** : `main/mission-control/mission-control-runs.ts` lit l'agent (provider, modèle,
  rôle, dernière tâche), le démarre, lance `runOneShotLLM` (prompt système du rôle,
  `requireProvider`, délai de 10 min, arrêt par `AbortSignal`) et envoie au backend la réponse par
  lots, l'usage rapporté par le provider puis `completed` ou `error` avec sa raison. Le backend
  garde la réponse (`output`, 20 000 caractères au plus), arrête le chronomètre, écrit un nœud
  « résultat » dans l'arbre et `agent_completed` / `agent_failed` dans le journal ; un compte
  rendu après un arrêt est ignoré. `core.oneshot.runs_own_agent` laisse passer un CLI qui a son
  propre client quand un projet et un dossier de spec sont donnés. La carte affiche la réponse,
  « En attente du modèle… » au lieu d'un pourcentage inventé, et un seul bouton Arrêter (un appel
  ne se met pas en pause). Toutes les requêtes de la page passent par l'IPC du main.
- **Vérification** : `pytest tests/mission_control tests/test_oneshot_usage.py -q` ;
  `cd apps/frontend && pnpm test -- mission-control ipc-channel-parity`.
